## 21.2 阶段拆解

### P0 — 工程骨架与 AI 真实接入（已完成）

**目标**：把「设计说明书」落地为可编译、可运行的工程骨架。

**交付物**：
- 后端 7 服务（gateway + user / history / knowledge / graph / ai / learning）Clean Architecture + DDD 落地
- 共享 `pkg/`（config / errno / gormutil / idgen / logger / outbox / pagination / rabbitmq / response / tracing）
- `deploy/docker/docker-compose.dev.yml` 一键拉起 8 个依赖（PG / Redis / Neo4j / Milvus / MinIO / Meilisearch / RabbitMQ / etcd）
- GitHub Actions 四条流水线（backend / frontend / mobile / commitlint）
- AI Service 的 LLM Provider 接入真实 HTTP 协议：OpenAI、Anthropic、DeepSeek、Qwen（DashScope 兼容模式）、Kimi、GLM

**验收标准**：`make backend-build` 全绿；`make backend-test` 通过；任一服务本地 `make run-*` 可启动并响应 `/health`。

---

### P1 — 存储与事件链路打通（已完成）

**目标**：把 knowledge-service / graph-service / ai-service 的三类「stub 占位」替换为真实协议客户端，让数据真正流动起来。

**任务清单**：

- [x] **knowledge-service · Embedding**：接入 OpenAI `text-embedding-3` HTTP API（沿用 ai-service `net/http` 直连模式，不引入 vendor SDK），保留 `provider=stub` 离线回退。
- [x] **knowledge-service · Milvus**：接入 Milvus REST API v2（`/v2/vectordb/entities/insert|delete|search`），实现 `EnsureCollection / Insert / DeleteByDoc / Search`，保留 `enabled=false` 内存回退。
- [x] **graph-service · Neo4j**：接入 Neo4j HTTP 事务 API（`POST /db/{db}/tx/commit` + Cypher），实现 8 类节点 MERGE / 9 类关系 MERGE / 复杂图查询，保留 `enabled=false` 内存回退。
- [x] **graph-service · RabbitMQ Subscriber**：补全 `Subscribe` 消费循环（dial → channel → queue declare → bind routing keys → consume → dispatch to handler），实现 nack 语义与 best-effort 启动。

**验收标准**：本地 `docker compose up` 拉起真实 Milvus / Neo4j / RabbitMQ 后，把对应 `enabled` 置 `true`，知识图谱 ETL 链路（`doc.indexed` 事件 → Neo4j 节点 upsert）端到端可跑。

### P2 — 业务闭环：History Service（已完成）

**目标**：中医发展史八大实体（朝代 / 学派 / 人物 / 著作 / 事件 / 方剂 / 药物 / 疾病）业务全链路。

**交付物**：43 条 HTTP 路由、12 张数据表、4 张关联表、Meilisearch 跨实体检索、MinIO 文件上传、RabbitMQ 领域事件发布。

**验收标准**：根 README 第 105 行标注的「History Service（已完成 P2）」。

---

### P3 — RAG 与 Agent 联调

**目标**：把 [06-RAG设计](./06-RAG设计.md) 与 [07-Agent设计](./07-Agent设计.md) 的端到端链路跑通。

**任务清单**：

- [ ] 文献上传 → MinIO 原文桶 → Markdown 抽取 → 切片 → 向量化 → Milvus 入库
- [ ] 用户提问 → query 向量化 → Milvus ANN + Meilisearch BM25 → RRF 融合 → 重排 → Agent Plan→Execute→Answer
- [ ] Agent 调用 Knowledge Service / Graph Service / Tool 的多阶段执行链路
- [ ] Prompt Center 模板治理（CRUD + 激活 + 变量渲染）

**验收标准**：上传《伤寒论》一份样本文献后，对「伤寒论中太阳病的代表方剂是什么」能给出有引用、有图谱关联、可追溯的答案。

- [ ] Learning Service：课程 / 课时 / 选课 / 学习记录 / 考试 / 错题 / 学习计划 41 条路由

**验收标准**：一个完整的学习者旅程——注册 → 选课 → 学习 → 考试 → 错题回顾 → 学习计划生成。

## 21.4 风险与依赖

| 风险 | 影响 | 缓解措施 |
| ---- | ---- | -------- |
| 离线开发环境无法 `go get` 新模块 | 阻断 vendor SDK 接入 | 全部采用 `net/http` 直连 REST/HTTP 协议，与 ai-service LLM Provider 模式一致 |
| Milvus REST API schema 复杂 | 向量化入库链路阻塞 | P1 先做 Insert/Delete/Search，EnsureCollection 走 describe-or-create |
| 国产 LLM 厂商协议差异 | AI 多模型切换成本 | OpenAI 兼容协议统一覆盖 DeepSeek / Qwen / Kimi / GLM |
| 移动端与 PC 端 API 重复封装 | 维护成本 | 共享 `packages/api` TypeScript 定义，移动端独立 Dio 封装 |
| 商业化阶段 AI 成本不可控 | 毛利压力 | P8 上线 token 计量与配额限流，参考 [08-MCP设计](./08-MCP设计.md) §8.5 |

## 21.5 决策记录

- **ADR-21-01**：所有外部 SDK 接入优先采用 `net/http` 直连 HTTP/REST 协议，不引入 vendor Go SDK。理由：离线开发环境约束 + 协议透明可调试 + 与 ai-service 既有模式一致。
- **ADR-21-02**：所有 stub 客户端保留 `enabled=false` 内存回退路径。理由：离线开发与单元测试可在无外部依赖下运行，与既有 `milvus.enabled=false` / `neo4j.enabled=false` 配置开关一致。
- **ADR-21-03**：移动端采用 Flutter 而非 React Native。理由：[13-移动端设计](./13-移动端设计.md) 已确定，性能与一致性更优。
